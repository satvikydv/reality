# Decisions

## 2026-10-28: pivot to memory-first (spatial memory as the headline)

**Decision.** The product headline changes from "guide and verify a physical task" to **spatial memory**: scan a room by panning the phone, find objects by what they do, get guided to them, and see what changed between two scans. Plan-and-verify (F3) stays as a secondary feature for the Best Agentic bonus. The brick-kit hero scenario is dropped. The scope, user stories, demo storyboard, requirements and risk list were updated; new requirements are F10 (room scan with orientation anchors), F11 (semantic find), F12 (guided retrieval) and F13 (what-changed).

**Why.**
- **Fits the rubric and the anti-project warning.** The original scope already says the value is memory, verification and the agent API, and that the product must never read as "a camera that labels things and chats". Memory, retrieval by function and change over time are the parts a plain image analyzer cannot do, and they give the Reality API a stronger story (an agent asking where something is or what moved).
- **Lower technical risk than the old hero.** The riskiest claim in the old plan was fine-grained step verification of brick placement (listed as a risk with a fallback hero task). Memory features rest on coarse, robust signals: object presence, rough direction and mask geometry.
- **The phone supplies the missing signal.** Orientation sensors give yaw/pitch/roll for every frame, so objects can be anchored to a direction in the room without SLAM, and guidance has a "target minus current heading" to point at.
- **Better demo.** A spoken functional query followed by an arrow that steers you to the object is understandable in seconds and works as the 30-second X clip. What-changed gives a second, different beat.
- **Cheap to scope.** Reuses what M0 is already building (SAM, Spark structured output, voice). Plan-and-verify code is not thrown away.

**Costs and constraints accepted.**
- Anchors are angular only. Translation is unknown, so guidance assumes the user rotates roughly in place and claims no distances.
- Orientation quality is unproven: magnetometer noise indoors and drift over a scan are M0 measurements (the `/orientation` page), and the lower-drift source is chosen from them.
- What-changed needs a shared yaw frame between scans (absolute source, or alignment from matched static objects).
- "Behind" cannot come from angular anchors alone and is marked [VERIFY].
- Schedule is tight: M4 now carries the Reality API, plan-and-verify and the open-weight backend in one day. The cut line was changed so F3 shrinks first among the kept features (after F9, F8 second option, F7 polish, F5).
- Priority changes: F3 moved from P0 to P1 (secondary), F5 watches from P1 to P2 (not in the new storyboard), F10 to F12 are P0 and F13 is P1.

**Implementation changes made with the pivot.**
- WS frame protocol is now `flags u8 | seq u32 | client_ts f64 | meta_len u16 | meta JSON | JPEG`. "Save sample" sends orientation (both sources) and camera info as `meta`; the server writes it to a `.json` sidecar next to each saved frame in `data/frames/`.
- New shared module `web/js/orientation.js` (yaw/pitch/roll of the rear camera from either source) and the `/orientation` drift test page.
- `scripts/sam_latency.py` defaults to desk-object concepts: keys, headphones, mug, notebook, remote control, water bottle, charger, scissors, laptop.

**Not updated (still describe the old hero).** The README M0 commands and the default task list in `scripts/spark_plan.py`. `scripts/sam_latency.py` has no labels file, so counting accuracy against a true count per frame is not implemented yet.

## 2026-10-28: laptop dashboard (replaces the TV view)

- **Laptop browser, not a 1920x1080 TV stage.** The Claude Design `tv.html` scaled a fixed stage; this is a fluid grid for a laptop window (min 1100x640), reusing the design's theme and `drawMap`. `/tv` and `web/tv.html` are removed.
- **One feed for everything**: the page opens `/ws/events` and renders the server's event stream (scan progress, `world_update` with live objects and coverage, find results, agent calls, guide requests). It keeps no state of its own, so replaying the last 200 events rebuilds the screen when it is opened late or reloaded.
- **Compare panel on REST**: `/api/scans` lists scans, `/api/changes?before=&after=` returns the same answer as the `what_changed` agent tool. Cards show before and after photos with the object boxed, grouped Moved, Removed, Added; `unverified` is only counted in the summary line.
- **Agent panel shows what the agent was told**: `agent_call` events now carry the sighting and object id, so the photo and the map highlight match the agent's answer.
- **Model text goes in with `textContent` only** (object names and answers come from a model). Replay photos can show people; the compare cards and the agent panel show them at thumbnail size, so shoot the demo scene without bystanders.
- **Bug found while screenshotting**: `ui.js` `fit()` resized a canvas only when its width changed, so a height-only layout change left a stretched drawing (duplicated compass labels). It now compares both.
- Checked in headless Chrome at 1440x900 with scripted data and with real events (a replayed scan, an MCP `where_is`, a compare of two stored scans). The compare on real data shows many moves because the two scans are unrelated (different frame sets); a controlled before/after scan is still to do.

## 2026-10-28: Reality API (MCP), event feed, agent guide requests

- **MCP over Streamable HTTP, mounted on the main app at /mcp**, not a separate process. A second process could not share the live event feed or reach the connected phone. Each startup builds its own MCP server because a session manager can only run once (this also lets tests start the app repeatedly). `python -m app.mcp_server` stays as a read-only stdio fallback.
- **Answers carry their own trust information.** `where_is` returns frames seen, best confidence, anchor spread, age, and whether the object is from the latest scan. A miss is `not_seen` with the latest scan's coverage, never "not there"; the server's instructions tell agents this explicitly. `what_changed` keeps `unverified` as its own group for the same reason.
- **Read-only except `guide_user_to`.** It resolves the query, then publishes `guide_request` on the event bus; every connected phone socket subscribes to that type only and the phone UI jumps to the Guide screen. With no phone connected it returns `no_phone_connected` instead of pretending. `get_frame` returns photos that may show people, so `REALITY_API_FRAMES=0` removes the tool.
- **DNS-rebinding guard stays on** (allowed hosts 127.0.0.1, localhost, ::1, plus `MCP_ALLOWED_HOSTS`); a request with a foreign Host header is rejected (tested over a real socket). Non-loopback binds still need `ACCESS_TOKEN`.
- **Event bus** (`app/events.py`): in-process pub/sub with a 300-event history, bounded per-subscriber queues that drop their oldest events, and an optional type filter. Scan progress, `world_update` (the live object list after each stored frame), find results and agent calls are published; `/ws/events` streams them to the laptop dashboard with the last 200 replayed, so a dashboard opened mid-demo catches up.
- **What-changed speech** groups repeated labels ("3 flags are gone") and stops after 6 sentences with "And N more changes", because one noisy scan produced a paragraph of duplicates when run on real data. The structured lists are complete.
- **Tried on real data**: the CLI client against the live server answered `scan_summary` and `where_is` from the stored office scan. The `what_changed` run compared two unrelated scans (a replay of different frames against the live scan) and reported many "moves"; it proves the plumbing, not the accuracy. A controlled before/after test (move two objects between two real scans) is still to do.
- Tests: `tests/test_reality_api.py`, `test_mcp_server.py` (in-process MCP client), `test_http_integration.py` (real sockets: phone, dashboard and MCP client on one app), `test_events.py`.

## 2026-10-28: auto capture and the live scan queue

- **The user never saves frames.** "Scan room" starts a scan, then the page watches the camera heading (`web/js/keyframe.js:KeyframePolicy`) and sends a keyframe when the camera has turned `stepDeg` (18 degrees, great-circle so pitch counts) from the last sent frame and the phone is steady (under 12 deg/s over the last 400 ms; between 12 and 30 deg/s a frame is only taken once 1.6x overdue; above 30 deg/s it says "slow down"). Min 500 ms between frames. The 12 deg/s limit comes from the manual run, where frames taken while turning at about 8 deg/s were visibly smaller JPEGs (203 to 224 KB vs 400+); not tuned beyond that [VERIFY on the phone].
- **Coverage ring on the phone.** 36 ten-degree compass bins, each keyframe fills +-15 degrees; the ring shows percent and heading, and the hint names the nearest gap ("gap 40 deg to the left"). The scan ends by itself at 97% or when the user taps Done. The server independently reports coverage from the frames it actually stored (`yaw_coverage`, +-0.4 x FOV), so a frame that failed server-side shows up as a gap in the summary.
- **Wire protocol.** Binary frames keep the existing header; flag bit 2 marks a scan keyframe (bit 1 is still "save sample"). JSON control messages: `scan_start`, `scan_end`, `find`. Server events: `scan_started`, `frame_queued`, `frame_rejected`, `frame_done`, `frame_error`, `scan_summary`, `find_result`, `error`. Replies without a `type` are the old M0 echo, so the dev tools still work.
- **Server queue.** `app/scan_service.py`: one `ScanSession` per socket, a bounded queue (32) and 3 workers running `ScanPipeline.process` concurrently, 4 SAM calls in flight in total. A full queue rejects the frame with a reason instead of blocking. `scan_end` waits for the queue (120 s cap), closes the scan and sends the summary; a dropped socket stops the workers and keeps what was stored. Progress lines go to the uvicorn log (`data/server.err.log` when started in the background).
- **Concurrent frames do not share new names.** A frame in flight cannot see names another in-flight frame is about to add, so the "reuse known names" hint helps less. Observed on a replay: "mouse" and "computer mouse", "phone" and "smartphone". `concepts.ALIASES` folds the common synonyms; the rest needs a smarter merge later.
- **Spark timeout cut from 60 s to 25 s** (`SPARK_TIMEOUT_S`; SAM client 30 s). One listing call took 64 s in the first replay (a stall, then the retry). Both are retried, so a stall now costs about 25 s, not 60.
- **Find results carry the replay frame** (`/world/frame/<id>.jpg` plus box and size); the page draws the box on it and speaks the answer with the browser's speech synthesis.
- **Verified without the phone**: `scripts/replay_scan.py` replays saved frames through the real WebSocket against the live APIs (11 clean frames: 11/11 stored, 13 objects, find worked, $0.10, 86 s of which 66 s was the one stalled Spark call). The page loads on the phone without errors. The auto-capture itself has only been tested as logic (`node --test tests/js/keyframe.test.mjs`), not with a person panning.

## 2026-10-28: Scan pipeline (F10)

- **Spark names, SAM boxes, World Model anchors.** `app/scan.py:ScanPipeline.process` resizes the keyframe (max side 960), asks Spark for the object types in view, runs one SAM concept prompt per name concurrently, drops boxes under `min_conf` 0.5, collapses overlapping boxes (`suppress_overlaps`: IoU over 0.6, highest confidence wins, the more specific label wins a near tie) and observes the rest. Boxes are anchored with the resized dimensions because SAM returns pixels of the image it was sent.
- **Concept prompts per name, not box batches (for now).** The original plan ("Spark lists, then box-prompt batches of 16") needs boxes from Spark, and Spark's box convention is unmeasured (`spark_grounding.py` has not run). One concept prompt per name costs one SAM request each ($0.0025) but needs no boxes. Switch when Spark grounding is verified.
- **A frame is stored only if every SAM call succeeded** (one retry each). A stored frame says "this direction was looked at", which what-changed uses to call an object gone; a half-failed look would fake that. The caller gets `FrameReport(stored=False, errors=[...])` and can retry.
- **Known names are fed back.** Names already in the scan are passed to Spark as "reuse a name from this list" to keep labels stable across frames (what merging depends on).
- **What it cannot do yet.** Spark forgetting to list an object means that object is not looked for in that frame, and coverage still counts the direction as scanned. Cable-like objects fragment into several boxes. Frames are processed in the order given and not deduplicated by pose. Not wired into `main.py`.
- **Refactor.** `sam_call` moved from `scripts/common.py` to `app/sam_client.py` (takes a data URL; closes the stream; never raises), prices to `app/pricing.py`. Scripts keep working through `common.py` wrappers.
- **Speech fix.** `where_is` no longer says "left of the water bottle" about a water bottle; it names a different object first, else "another water bottle".

## 2026-10-28: orientation source = absolute

On the Realme RMX2001 the "relative" sensor is not gyro-only: both sources gave the same yaw (to 0.01 degrees) and under 0.5 degrees of drift over three 360 degree turns (`docs/measurements.md`). The pick is a tie, so use the absolute source: it keeps a shared yaw frame between scans. `app/changes.py:estimate_yaw_offset` stays as the fallback for devices where the relative source has its own zero. Heading error mid-turn (magnetic distortion) is not measured yet, so `MOVE_DEG` and `merge_deg` stay placeholders.

## 2026-10-28: Guidance and what-changed (F12, F13)

- **Guidance in image axes.** `app/guidance.py` expresses the target direction in the camera's right/up/forward basis, so the overlay arrow (`arrow_deg`, clockwise from up) and the hint ("Turn right", "Tilt up", "A bit more left", "Almost there, a little right", "Turn around", "That's it.") stay correct when the phone is rolled or pitched steeply. `dyaw`/`dpitch` are returned for display only. Hint bands (`ARRIVE_DEG` 6, `FAR_DEG` 45, `TURN_AROUND_DEG` 110) are untested guesses until a person walks it [VERIFY]. No smoothing of the live heading yet; add it if the arrow jitters on the phone.
- **Yaw frames need an explicit offset.** The relative sensor's yaw zero is arbitrary per session, so a stored anchor is mapped to the live frame with `yaw_offset` (live minus scan). `app/changes.py:estimate_yaw_offset` finds it by majority vote over same-label object pairs (most agreeing objects, then the smallest rotation), so a few moved objects do not spoil it. It reports `confident` only with two or more agreeing objects; with one shared label a moved object cannot be told from a rotated frame. Pitch is gravity-referenced and is not shifted.
- **What-changed matches by label, then angle.** Pairs are taken nearest-first across scans (label match score above 0). A pair closer than `MOVE_DEG` (15 degrees, placeholder until the drift measurements are in) is unchanged; farther is moved. Leftovers are added or removed.
- **Coverage guard.** Removed and added are only claimed if the other scan's frames actually looked at that direction (projected inside the image with a 5% margin). Otherwise the object goes to `unverified` and the spoken summary says part of the room was not scanned both times. This prevents the commonest false alarm: a partial second scan.
- **Known limits.** A label that vanishes in one place and appears in another reads as "moved"; swapping two identical objects is invisible; appearance is not compared; the coverage test ignores occlusion. Both modules are pure logic and are not wired into `main.py` yet. `WorldModel.list_frames` was added for coverage. Tests: `pytest tests` (60 pass).

## 2026-10-28: Reasoner and semantic resolver

- **Reasoner interface.** `app/reasoner/`: a `Reasoner.respond(messages, tools, schema, effort)` protocol with neutral message parts (`text`, `image`). `MetaApiReasoner` uses the Responses API with strict `json_schema`; `OpenAICompatReasoner` uses Chat Completions for Modal Glimmer and Baseten Spark Open and is only mock-tested [VERIFY live]. `make_reasoner()` picks by `REASONER_BACKEND`. Every call goes through `with_retries` (429, 5xx and connection errors; exponential backoff with jitter; honours `Retry-After`). `MetaApiReasoner` refuses any model id containing "contributor".
- **Resolver judges the raw phrase.** `clean()` checks SAM-friendliness before normalising, because normalising strips the commas that make a phrase unfriendly (caught by a test: "a, b" became "b").
- **Skip the model for exact labels.** If the query is already a known label, `semantic_find` goes straight to the World Model. Only whole-query matches skip; "where are my keys" still goes to Spark.
- **Not-in-memory is explicit.** A resolved concept with no World Model hit returns `needs_live_look`; the SAM live-lookup step is not built yet.

## 2026-10-28: World Model and anchoring (first memory-first build)

- **Anchors are directions, not positions.** `backend/app/anchoring.py` turns a pixel plus the frame's camera pose (yaw, pitch, roll) into a world (yaw, pitch) with a pinhole model. Image roll is sensor roll plus `screen.orientation.angle`, assuming Chrome rotates the video with the screen [VERIFY]. `DEFAULT_HFOV_DEG = 60` is a placeholder until the phone is calibrated [VERIFY]; every frame stores the FOV it was anchored with.
- **Identity inside a scan.** A detection joins an existing object with the same normalised label within `merge_deg` (default 8 degrees) of its anchor; two detections in one frame never merge. The anchor is a confidence-weighted mean and `spread_deg` records the worst disagreement, which doubles as the anchor-error metric for the README. Appearance re-identification and cross-scan matching are not built.
- **"Where" is relative to the scan start.** The spoken description uses the yaw offset from the first frame of the scan, so it works with the relative source (arbitrary yaw zero) as well as the absolute one. Pitch is absolute (gravity-referenced).
- **Relations from anchors only.** `neighbors()` gives left of / right of / above / below / next to. "On" and "behind" need masks or depth and are not produced yet.
- **Frames on disk, rows in SQLite.** JPEGs go under `frames_dir/<scan>/<frame>.jpg` so a find query can return a replay frame; no pruning yet (about 60 frames per 30 s scan at 2 fps).
- Not wired into `main.py` yet. Tests: `pytest tests` (28 pass).

## 2026-10-28

- **Identity by footprint, not by centre.** Matching a detection to an object by the distance between box centres split big or cut-off objects: a laptop half out of frame has a centre many degrees from its whole-view centre, so one real scan gave 64 objects (14 laptops). Detections now carry an angular footprint (`anchoring.box_extent`); an object keeps the largest footprint seen and a detection joins it when it covers at least half of the smaller of the two (and a tenth of the larger, so a small box inside a big one is not swallowed). The centre rule within `merge_deg` stays as the fallback.
- **Parts of one thing.** SAM boxes the screen and the base of a laptop separately. `scan.merge_parts` unions same-label boxes in one frame that overlap by a third of the smaller box. Different labels are never merged (a cup in front of a laptop).
- **Fragments do not start objects.** A small box touching the image border can join an existing object but never creates one; the neighbouring frame sees the whole thing.
- **Consolidation.** Frames finish out of order, so `WorldModel.consolidate` re-merges same-label objects with overlapping footprints after every stored frame and at scan end. Two objects detected in the same frame are never merged: one view cannot see an object twice.
- Result on the stored scan 4 (79 detections, 16 frames): 64 objects, 14 laptops became 44 objects, 4 laptops. Comparing a scan with a reversed-order replay of itself now reports 0 moved (it reported many before). Not solved: results still depend a little on arrival order, and the FOV is still the 60 degree placeholder (at 45 degrees the same data gives fewer objects).

- **World-locked overlay.** Objects are drawn from their stored direction through the live pose, never from a distance (none exists). The outline is the stored mask warped with the rotation-only homography `H = K_cur B_cur^T B_cap K_cap^-1` (translation is unknown, so objects nearer than a few metres will drift when the user walks; they are meant to be viewed from where they were scanned). Without a mask the angular footprint is projected instead. Masks are kept as at most 32 polygon points per observation (`observations.poly`, added by an automatic migration); a merged box has no single mask, so it falls back to the footprint.
- **One FOV for both sides.** The server anchors detections with `HFOV_DEG` and serves the same value in `/api/overlay`; the phone projects with that value. An uncalibrated FOV shifts overlays away from the objects, so the dev menu says so and `scripts/calibrate_fov.py` computes the value from two ruler photos.
- **Hide rather than guess.** `uncertainty_deg` is the spread between an object's sightings; above 12 degrees the object is not drawn. Opacity holds for 30 s since last seen, then fades linearly to 25% at 30 minutes.
- **Overlay follows the raw sensor pose** (no smoothing) so objects do not swim against the video; the design's smoothed pose and its moving optical centre were dropped for the same reason. The design's linear degrees-to-pixels placement was replaced by the real projection.
- **UI from the design project.** The HUD (compass tape, horizon, pitch ladder, edge arrows, bearing dial, quick-ask chips) is the design's; the accent is blue on the phone and stays amber on the laptop dashboard (`--accent`).

- **Identity is a function of the detections, not of arrival order.** Frames finish out of order, so an online "match to the nearest object" gave different objects for different delivery orders (the old behaviour changed the result in 2 to 5 of 8 shuffled orders). Every detection is now stored (`detections`), and after each frame the scan's objects are recomputed from all of them in capture-time order (`memory.cluster`); observations and objects are derived tables. Capture time is the phone's, shifted by a per-scan clock offset so it sits on the server clock. Ids are kept by matching a recomputed object to the old object that shares most detections. Cost: a rebuild is quadratic in a scan's detections (milliseconds at the sizes seen).
- **Appearance as a veto only.** A colour histogram of each mask (hue by two saturation levels plus three grey levels) can refuse a merge the geometry allows; it never causes one, so a threshold that is too high creates duplicates. On the larger real scans (2, 4, 5) the median merged pair scores 0.59 to 0.83 and the least similar merged pair 0.37 to 0.59, while different same-label objects have a median of 0.46 to 0.57, so colour alone cannot separate things like cables; the threshold is 0.35, which vetoes none of the merged pairs but leaves only a thin margin on scan 2 (0.37). In simulation it cuts wrong merges between look-alike twins from 17% to 2%.
- **Edge-clipped detections** (small boxes touching the image border) no longer vanish: they join a matching object at once and become an object of their own when seen in two frames. In simulation this only matters when objects are seen once or twice (60 degree steps: missed 4% to 1%).
- **Anchor uncertainty = spread across sightings combined with FOV error.** The FOV error of a detection is its angle from the optical axis times the FOV's relative error (2% when calibrated, 10% for the 60 degree placeholder), so objects at the edge of the image are less certain than ones seen head-on. The guide arrow's cone is asin(uncertainty / distance): narrow when far, the full half-turn once nearer than the error.
- **One coverage definition**, in Python and JavaScript, tied together by golden values, with pitch bands. Yaw coverage (the ring, auto-finish) counts a frame at any pitch; bands say whether the floor and ceiling were looked at.
- **The camera is locked and guarded.** The FOV is only valid for the camera state it was measured in, so calibration records resolution and zoom, the app pins zoom to 1x and compares the track settings (and the video size, which changes on rotation) before and after every frame, and the server compares each frame's camera state with the calibration. A mismatch stops the scan with the difference named; nothing is silently anchored with a wrong angle. Not verified on the phone yet: how Chrome reports portrait dimensions in `getSettings()` (the video-size check is against the video element's own size at lock time, to avoid a false alarm).
- **The memory is evaluated on simulated rooms** (`app/simworld.py`) because duplicate rate and id switches need ground truth. Simulated detections have jitter, misses, clipping and colour noise but are not SAM output, so the numbers show the memory logic, not end-to-end quality.

## 2026-10-29: first run, permissions and navigation

- **Nothing media-related runs on load.** The page used to start the camera and the sensors in `boot()`. Now Home has no camera (a plain background), and `CameraSession.acquire()` is called only from a tap on New scan, Find something or Guide me. The Find screen (`ask`) is the old home with the camera: input, chips, AR toggle. An agent's `guide_request` now opens the result and asks for a tap on Guide me instead of turning the camera on by itself. `tests/test_entry_flow.py` replaces every camera, sensor, microphone, wake-lock and orientation-lock API by a spy before the page's scripts run and asserts the log is empty after load (and that the spy does see a real tap, so an empty log means something); injecting an auto-start made it fail, as intended.
- **The intro is a layer over Home, not a different landing page.** First visit: three cards (what it does, how to scan, data), then a primer, then the browser's prompts. Skipping the intro still sends the first camera tap through the primer. State lives in `localStorage` (`ros.onboarded`, `ros.primed`); if storage is blocked it lives in memory for the session. Replay from Settings changes no stored state.
- **Camera lifecycle in one class.** `CameraSession` owns start, release, the wake lock and the portrait lock. Leaving a camera screen, `visibilitychange` to hidden, `pagehide` and a track that ends by itself all release it; coming back never restarts it. Sensors are started in the same tap, before awaiting the camera, because iOS only allows its motion prompt inside the gesture. The wake lock is held on all three camera screens, not only while scanning, because the screen turning off during a guide kills the camera just the same. Portrait lock is best effort (most browsers refuse it outside fullscreen); the camera guard and a "hold the phone upright" hint cover the rest.
- **A scan that cannot continue now ends properly on the server.** `abort()` (camera changed, page hidden, link lost) used to leave the server session active, so the next scan failed with "a scan is already running". It now sends `scan_end` (kept) or, if the server had not confirmed the start, `scan_cancel`. Cancel is a new message: the server stops the workers and deletes the scan; the phone asks for confirmation first.
- **Status check that never blocks Home.** `/api/status` answers "checking" after 1.5 s while the key check (one authenticated model list, cached 5 min, 20 s after a network failure) finishes in the background. States: ok, set (key present, the API has no cheap check, so not verified), missing, invalid, unreachable. Scan and Find are disabled only for missing or invalid.
- **"Not found" says what it did not check.** `find_result` carries `checked` (scans, covered degrees, scan id) when nothing is found, and the page says how much of the room that scan covered and that nothing is checked live.
- **Deleting a scan removes its frames, detections and objects, and only files recorded for it inside the frames folder** (no recursive delete).
- **Processing has real progress and a way out.** Progress is frames answered over frames sent. After 30 s without any progress, or 150 s in total, the page offers "Check the server", which rebuilds the summary from what the server stored (for a dropped link), and "Go home".

## 2026-10-29: rooms ("spaces")

- **A room's memory is its latest saved scan.** Older saved scans stay only so What changed can compare. Before, every question searched all scans and fell back to older ones, so a scan of the office answered questions about the bedroom. `where_is` now searches one scan, which callers take from a room; the old "earlier scan" fallback is gone. Rooms share nothing: identity (objects are per scan), overlay, guidance and comparison all resolve a room first, and a scan id from another room is refused (`wrong_room`, HTTP 400).
- **Save and Discard.** A live scan is a `draft` until the user saves it after the review; a draft is not memory. Discard deletes a draft; a saved scan is deleted from the room's history. A scan cut short (page hidden, link lost) stays a draft in its room, marked UNSAVED, so nothing found is silently lost or silently trusted.
- **The user sets the active room, explicitly.** Creating a room does not activate it; the wizard asks. Find, Explore, Changes and the Reality API default to it. With no active room and none named, every MCP tool answers with the room list instead of guessing. Cross-room Find is read-only, grouped per room; opening a result from another room asks to switch first. Guidance works only inside the active room (`POST /api/guide`, and `guide_user_to`, refuse otherwise).
- **Migration.** Scans from before rooms go into a room named "Unassigned", saved and not active, on first open of an old database. A fresh database has no rooms.
- **Baseline.** What changed compares the latest saved scan with the room's baseline if one is set, else with the scan before it. Confirm / dismiss marks are stored per (room, two scans, change key); keys are stable object ids.
- **Deleting a room erases its scans, frames, photos, detections and objects**, file by file inside the frames folder only (no recursive delete). Delete all data does the same for every room.
- **Screens, state and data are separate so a re-skin is easy.** One registry (`screens.js`) lists every screen with its states, tab, camera rule, data and API; markup shows states with `data-show` and binds taps with `data-act`; render functions take `(state, data)` and run on real data and on demo fixtures alike; colours, radii, spacing and type are tokens in `theme.css` and styles live in `app.css`. Tests fail if the registry, the markup, the fixtures or `docs/screens.md` disagree, and a real-browser test opens every screen in every state.
- **The camera moved off Find.** Find is a text search with no camera. The camera screens are the live scan, Explore (AR) and Guide me, and each starts only from a tap.
- **Test runs must be silent.** The browser tests record speech instead of playing it and run the browser muted: a first version spoke the demo answers through the laptop's speakers.

## 2026-10-29: objects inspector and the calm overlay

- **Corrections are constraints on detections, not edits of objects.** Objects are recomputed from every stored detection after each frame, so editing an object row would be undone by the next frame. A correction is stored (in `corrections`, in order, with its source) as a set of detection ids and handed to the clustering as a constraint: merge groups are forced into one object, detached detections stand alone, deleted detections and the detections of a label marked "not an object" in the room are ignored. A later correction wins over an earlier one (merging an object back after a detach puts the sighting back). Deleting an object ignores its existing sightings only; a new sighting of the same thing in a later frame is a new detection and can make a new object.
- **A sighting's id is its detection's id**, because observations are rebuilt and their ids change; detections are the stable record.
- **Decisions come from the log, or are recomputed.** `WorldModel.decisions()` is an in-memory log (lost when the server restarts); when it is empty for a scan the inspector recomputes the decisions from the detections and the corrections (the clustering is deterministic), so any scan can be explained at any time. Decisions now carry the detections involved, so an object's decision list can be filtered.
- **Possible duplicates** are same-label objects within 20 degrees that were never seen in one frame (two objects seen together are two objects), scored by direction gap and footprint overlap, halved when the colours disagree. They are suggestions; merging is the user's call.
- **"Not an object" is per room**, applies to every scan of the room and to future scans, and is reversible. Nothing is deleted: the detections stay and are ignored.
- **Calm is a selection, not a filter on drawing.** `calm.js` chooses (hide low confidence, uncertain and background classes; score confidence x centrality x recency; group duplicates; place labels without overlap, dropping a label rather than drawing it on another; one outline), `ar.js` only draws what it is told. Only the chosen object's mask is projected, from a simplified and rounded polygon; the others are positions. The Find / Guide target is always labelled and outlined, whatever its score.
- **All thresholds are in one file** (`overlay-config.js`); the three modes share the label-size and scoring constants.
- **Quick ask is a bottom sheet in every mode**, not only in Calm: the Find screen no longer has a row of chips.
- **Measured honestly.** On the three stored scans the label reduction comes from the label limit, grouping, off-screen objects and collision avoidance; the confidence and background filters hide nothing there because the scans contain neither. See `docs/measurements.md`.

## 2026-10-30: notes in places, ask the room, rewind, caregiver view

- **One vantage point, still.** All four features rest on the same memory: directions seen from where the scans were made. Notes are anchored to a direction, or to the object under the reticle (the note then takes that object's direction); they are right from roughly where you stood. Nothing here claims world-locked tracking.
- **Ask the room reasons over text.** Object names, directions, nearby objects, and the changes between earlier saved scans go to the model as text inside a delimited block; the model is told object names are data. It may only name ids that exist in the room, and anything else is dropped. No image is sent, so no consent question arises. "On" is never claimed (no surfaces exist), only "near" or "in the same direction as".
- **Rewind reuses Changes.** The earlier scan is aligned with the same landmark alignment, so ghosts are in today's directions. A direction today's scan never looked at gives "was here?", not "gone": absence there proves nothing.
- **Caregiver view is memory, not tracking.** It shows what the last scan of each room saw, with the photo and the time, and says so on every answer. It is off until the person turns it on in their phone's Settings; until then the dashboard shows the list but no places and no photos. The consent is a gate in this app, not a login: on a shared computer it protects against accidents, not against someone with access to it. Alerts: not seen in any room's last scan (with the rooms' coverage), last seen in a room other than the usual one, last seen more than three days ago (`CARE_STALE_DAYS`).
- **Older scans are history.** A watched item is looked up only in each room's latest saved scan; an older sighting does not count as where it is now.
- **Delete all data** also erases notes, the watch list and the consent.

## 2026-10-30: viewpoint-robust alignment and the rescan assist

- **Align from the pictures, not only from the objects.** Comparing two scans by the directions of the objects cannot tell a moved scan from moved objects: both look like objects at new directions. `app.align` recovers the offset between the scans' frames from the images (SIFT, ratio test with a mutual check, RANSAC), pair by pair, then combines the pairs with an inlier-weighted median. It is OpenCV and NumPy on the CPU; the rotation fit is our own (bearing vectors and a Kabsch fit inside RANSAC), next to OpenCV's essential matrix.
- **Rotation model unless the essential matrix explains clearly more.** A phone turning on the spot is a pure rotation, for which the essential matrix is degenerate; a step sideways is not. The rotation model is used unless the essential matrix explains at least 15% more matches, and only then is a translation direction reported (its size is unknown, so only "which way"). The remaining parallax (how far features sit from where the rotation alone puts them) is reported too: it is the measure of how far the viewpoint moved.
- **The offset comes out as yaw, pitch and roll, with yaw in the convention of Changes (B minus A).** Pitch and roll offsets are near zero for a normal yaw-only difference: a per-frame sensor tilt error is not a different reference frame. Detected objects are masked out of the features, so things that moved do not pull the alignment.
- **Quality is good, weak or failed, and it gates what may be said.** Good needs at least 3 frame pairs, 100 inliers and a spread of 2 degrees or less. When it is weak or failed, nothing is called moved, new or removed: those objects go to "can't compare" (an object still within tolerance is unchanged). If the pictures cannot be matched at all the objects' own directions may still give an offset, but it is never trusted enough to call a move.
- **Coarse to fine.** Frames to compare come from a pose prior (viewing directions that roughly agree, assuming the compass was shared). If that does not give a good result it is refined around the offset it found, and if that is not enough a coarse search over sampled pairs finds the offset (a scan started facing another way). A time budget stops it at 25 seconds with what it has. The result for a pair of finished scans is stored.
- **Tolerance depends on distance.** Spark's name pass now also returns a typical size in centimetres per label (stored as a running geometric mean; a built-in table and then 30 cm cover labels it did not size). A box and the size give a distance with a band (size good to about a third, the box to a twelfth). A viewpoint error (15 cm by default, `VIEWPOINT_ERROR_CM`) moves an object by atan(error / distance) in the picture: a mug an arm away allows about 8 degrees, a plant across the room about 2. When the direction of the viewpoint change is known only the part across the line of sight counts, never less than a third.
- **Classes.** Unchanged within the tolerance; possibly moved up to twice the tolerance or the tolerance plus the uncertainty (distance band, anchors, alignment spread), whichever is larger; moved beyond that. New and removed need the other scan to have looked in that direction. Nothing here ever reports a distance, only angles.
- **Rescan assist.** Before a rescan the room's first keyframe is shown as a 30% outline over the camera; about twice a second the phone sends a small live frame and the server answers with words and numbers (turn, tilt, roll, a direction to step). It is image-only, so it works when the compass differs. Start is never blocked: it reads Start anyway until the view is within 4 degrees of turn, tilt and roll and the parallax is under 1.5 degrees.
- **Honest limits.** Not verified on the phone. Real parallax makes near objects look like they moved; the essential matrix handles it for the alignment, but the tolerance is a model (assumed size and viewpoint error), not a measurement. A scene with little texture, or two scans with different lighting, can fail to align: that shows as failed and nothing is called moved.

## 2026-10-31: near-field alignment, local evidence, evidence for gone and new, "moved, low confidence", scan quality

Real desk scans (40 to 60 cm, 3 to 4 frames, tilted down) aligned only weakly: 1 of 12 frame pairs matched, so by design nothing was called moved and a moved mouse was missed. A depth-rendered desk (`tests/synthetic_world.DeskScene`) reproduces that (the old code: good in 10 of 50 runs at the texture level that matches the real pair statistics, 0 of 10 moved mice found), and every change below was measured on it before and after. All numbers are synthetic; see `docs/measurements.md`.

- **Features on objects are kept, not masked** (`align.extract`, `ALIGN_VERSION` 3). Masking every detected object's box, padded, left almost nothing at a desk, where the objects are most of the picture: a frame pointed at the laptop kept 2 matches. That was the main cause of the weak alignments. Features are now labelled with the box they fall in. A moved object must still not pull the estimate, so when one object holds more than half of a pair's inliers (`DOMINANT_SHARE` 0.5) the pair is refitted without it; the full fit is kept only if the rest of the scene agrees within 1 degree (`DOMINANT_AGREE_DEG`), else the refit is used, and with nothing else to go on the pair is dropped. `mask_objects=True` keeps the old behaviour for comparison.
- **Every pair for small scans.** When `frames_a x frames_b <= 64` (`ALL_PAIRS_MAX`) every pair is tried; the pose-prior shortlist (3 per frame) missed pairs that matched.
- **An honest standard error.** Pairs that share a frame share that frame's sensor error, so the standard error of the offset counts distinct frames on the thinner side, not pairs, and the scatter is never taken as less than 1 degree (`PAIR_NOISE_FLOOR_DEG`): two pairs that happen to agree had reported a standard error of 0. Quality still needs it at most 1.5 degrees (`GOOD_SEM_DEG`, unchanged since 2026-10-30; the entry of that date says "a spread of 2 degrees", which the code replaced with this standard error then). A 3-frame rescan therefore often comes out weak: that is the evidence being thin, and the scan quality card asks for more frames.
- **Per-frame poses and the tilt bias.** Each frame of the later scan gets its pose in the earlier scan's frame from the pairs it is in (`frame_poses`); its objects are re-anchored through those poses, which removes its own sensor error and a tilt bias of the whole scan (`pitch_bias_deg`, recovered within about 2 degrees of a simulated 4-degree bias). Used when the alignment is good, or weak but within 10 degrees of the compass.
- **Local evidence for each object.** For every frame pair, the matched static features in a ring around a detected object's box (not on it: if it moved its own features moved too) predict where its centre should appear in the other frame (`align.local_predictions`, a similarity fit, at least 6 features). They sit at about the object's depth, so they carry the same parallax: the difference from where the other scan really detected it is a pure image measurement, with no sensor pose and no assumed viewpoint error. Its tolerance is the largest of 3 degrees (`LOCAL_MIN_DEG`), 3 times the features' own scatter (`LOCAL_SPREAD_K`) and 0.7 of the object's size in the picture (`LOCAL_SIZE_SHARE`): a box centre is not a fixed point (a tall object shows new sides and stands above the desk texture), and over 80 static object comparisons the worst was 0.62 of the object's size (a cup) while moved objects were at 2.05 or more. Within that tolerance the object is unchanged whatever the assumed viewpoint error says. Beyond 2.5 tolerances (`LOCAL_MOVED_K`) it is a move, called "moved" only if the viewpoint model under the assumed 15 cm also allows it, so neither measurement alone makes the claim. In between the viewpoint model decides as before. This is what finds the mouse: 24 to 29 degrees away from where the desk around it says it should be, against a tolerance of 4 to 9 (five synthetic runs).
- **The viewpoint change is measured, not only assumed.** Objects the local evidence shows as static say how far the viewpoint really moved (their shift times the far end of their distance band). The viewpoint model then allows the larger of that and `VIEWPOINT_ERROR_CM`, up to 60 cm (`MAX_VIEWPOINT_CM`). On the simulated 20 cm step of seed 1 this measured 20.0 cm; before it was added, that step was the one false move in 50 synthetic scenario runs.
- **Gone and new need evidence** (`MIN_FRAMES_FOR_GONE` 2). Spark and SAM do not list the same things every scan, so "removed" and "new" now need the object seen in at least two frames of its own scan, the other scan to cover that direction, and (when the alignment carries local evidence) the other scan to have matched the texture at that spot. Otherwise it is "can't compare" with the reason ("seen only once in the earlier scan, so missing it now may just be a missed detection"). Objects of one label that were never seen in the same frame and lie within the viewpoint tolerance of each other count as one thing split by hand drift: they do not make the label "repeated", and an unmatched twin of a compared object is not called gone. Objects seen together in a frame, or far apart, are still several, so the rule from the office scans (several of a kind: never "moved") stands.
- **"Moved, low confidence": a decision for the owner, on by default, off with `MOVED_LOW_CONFIDENCE=0`.** A separate list (`moved_low_confidence`), its own amber group on the phone and the dashboard, its own sentence ("seems to have moved … check it"), never mixed into Moved. It is the only claim made from a weak alignment, and only when all of these hold: the alignment is weak, never failed; its offset agrees with the compass within 10 degrees (`LOW_CONF_MAX_OFFSET`: two independent sources agree) and rests on at least 40 matching points (`LOW_CONF_MIN_INLIERS`); the label is not repeated; and the shift is beyond 3 tolerances plus the alignment's uncertainty, taken as at least 2.5 degrees (`LOW_CONF_K`, `LOW_CONF_UNC_FLOOR`). With local evidence that means the residual beyond 3 local tolerances plus 2.5 degrees and the shift beyond one model tolerance plus 2.5; without it the shift beyond 3 model tolerances plus 2.5, which near the phone (a 17-degree tolerance at 50 cm) never happens. Why on: in the real desk case the offset was right to 0.6 degrees and the mouse moved about 27; saying nothing there is a missed change the caregiver story depends on. Why it may be wrong: a weak alignment can rest on one wrong pair (in the old code one such pair was 20 degrees off), which the compass check and the 40-point floor are there to catch. In 50 synthetic runs per texture level it fired 2 to 5 times, every time on an object that really moved, never on a static one; on a phone this is unmeasured.
- **Scan quality coaching** (`app.scan_quality`, the review screen). Advice, never a block on Save: at least 5 frames (arithmetic from the standard error, not a measurement: the synthetic desk did not show a clear frame-count effect), every shot within half a field of view of another, 60% of objects in two shots (the rule for gone and new), 60 or more background features per shot, else "tilt up a little so the far wall is in view" when looking down, and no more than a third of the shots blurred against the scan's own sharpest.
- **Ask and safety.** A question about safety ("what is unsafe in here") gets the model told it knows only names and directions, to say "might need a look" and never call anything safe, and the answer always ends with "This comes from the names in the last scan only; it is not a safety check." whatever the model wrote.
- **Demo mode tells the caregiver story.** The phone's demo room has pills and a stove (replacing a second bottle and the lamp, so it still has 16 objects), demo Ask follows the question, demo Rewind shows the pills' earlier place, and `/dashboard?demo` shows the caregiver view with made-up data. All of it is marked demo.
- **Honest limits.** None of this has been run on a phone or on the real scans (they are not in the repo). The local tolerance share (0.7) and the low-confidence thresholds are set on boxes rendered in a synthetic world; SAM boxes on real objects jitter more, and that is the first thing to measure. The memory still splits a near object into two when the hand drifts (its merge distance is 8 degrees); the comparison now copes with that, the memory does not.
